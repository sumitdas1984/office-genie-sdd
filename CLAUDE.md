## Architecture

### Processing Pipeline

```
Employee Input → FastAPI → Pydantic Validation → LLM Classification (stub) → Routing Logic → Acknowledgment Response
```

Current implementation: `POST /api/submit` follows this sequence: Pydantic validation → stub LLM call → stub routing → SubmitResponse.
Full LLM integration coming in FEATURE-002.

### Backend Structure (`src/`)

- `api/` — FastAPI routes, Pydantic request/response models, exception handlers
  - `models.py` — CategoryEnum, SubmitRequest, SubmitResponse, ClassificationResponse, ExtractedFields, RequestStatus, RequestStatusUpdate
  - `routes.py` — POST /api/submit endpoint
  - `exceptions.py` — Validation exception handler (returns HTTP 422)
- `middleware/` — Starlette middleware
  - `logging.py` — RequestIDMiddleware (extracts/generates X-Request-ID, stores in context)
- `services/` — Business logic stubs (full implementation in future features)
  - `llm_service.py` — LLM classification stub (FEATURE-002)
  - `routing_service.py` — Routing stub (FEATURE-003)
  - `id_generator.py` — Generates sequential request IDs (REQ-YYYY-NNNN)
- `main.py` — FastAPI app with RequestIDMiddleware and validation exception handler mounted

### Key Data Contracts

**SubmitRequest** (employee-provided):
- `employee_id`, `employee_name`, `employee_email`, `department`, `message`

**SubmitResponse** (returned by POST /api/submit):
- `request_id`, `status` (RequestStatus), `category` (CategoryEnum), `subcategory`, `extracted_fields`, `suggested_response`, `routed_to`, `created_at`

**LLM Response Schema** (returned by llm_service, parsed into dict):
```json
{
  "category": "IT|HR|Payroll|Admin",
  "subcategory": "string",
  "confidence": 0.0-1.0,
  "extracted_fields": { "date_mentioned": null, "system_name": null, "urgency": "low|medium|high", "error_message": null },
  "suggested_response": "string",
  "routing_target": "string"
}
```

**Request ID format:** `REQ-YYYY-NNNN` (auto-generated by id_generator, not client-provided)

**Status values:** `acknowledged`, `in-progress`, `resolved`, `closed` (defined in RequestStatus enum)

**Status workflow:** `acknowledged → in-progress → resolved → closed` (transitions will be enforced in FEATURE-003)

### Routing Logic (stub)

Current stub implementation: generates routing target as `{category}-team` with `-escalation` suffix if `urgency=high`.
Full automation rules coming in FEATURE-003.

### LLM Failure Handling (stub)

Current stub always returns success. Full retry/backoff/fallback logic coming in FEATURE-002.

### Request ID Middleware

- Every request gets a UUID4 `X-Request-ID` header (generated if not provided, extracted from incoming header if present)
- Available to handlers via `get_request_id()` from `src.middleware.logging`
- Returned in response headers
